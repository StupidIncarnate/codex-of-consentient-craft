# init, prompts and MCP — walkthrough

Case prefix: `IN` · Packages: `cli`, `hooks`, `mcp`, `orchestrator`, `siegelense`, `shared` · Main sources: root
`CLAUDE.md`, `packages/{cli,hooks,mcp,orchestrator,siegelense}/CLAUDE.md`, `scrolls/consolidated-plan-handoff.md`,
`packages/shared/src/statics/{session-snippet,mcp-tools}/*.ts`

## What changed

The legacy pt-N dispatch path is gone end to end: the `run-ward` and `run-riftcarver` MCP tools, their NextStep
variants, `operationStatus` and the `partial` signal are all deleted (`scrolls/consolidated-plan-handoff.md`,
"Finish" section). `mcpToolsStatics.tools.names` (`packages/shared/src/statics/mcp-tools/mcp-tools-statics.ts:17-42`)
now lists exactly 24 tools, and neither legacy tool appears in `.claude/settings.json`'s
`permissions.allow[]` in this checkout. The `SubagentStop` hook's block message now asks only for
`signal-back` with `signal: "complete"` and states plainly that it "takes no outcome field"
(`subagent-stop-block-message-statics.ts:28`) — the old `operationStatus` ask is gone (per the task brief, landed at
`bcdc89157`). The sign-off retirement that `consolidated-plan-handoff.md` flagged as still-stale mid-session is now
clean: `flowEvidenceContractStatics.judgingMarkdown` (`packages/orchestrator/src/statics/flow-evidence-contract/flow-evidence-contract-statics.ts:30-33,108-111`)
states outright "THERE IS NO PARENT, NO THREE-TRACK SIGN-OFF" and "there is no parent to hand one to" — the
`get-qa-checklist` mention is gone too. `siegemaster-reviewer` no longer exists anywhere in live `packages/*/src` —
it survives only as a name in historical scroll/plan documents and in `agentPromptClassificationStatics`'
`UNSERVED_PROMPT_NAMES` list (a deliberate compatibility shim for an already-run quest, not a live prompt). The
`dumpster-create-prompt-statics.ts` template is ~64KB of source (comfortably over `mcpToolResultStatics.maxVerbatimChars`,
50,000) and stays uncapped by design, because it is composed inline into the `/dumpster-create` slash-command body
rather than served through `get-agent-prompt`.

## Setup

1. This repo has already been through `dungeonmaster init` — `.claude/settings.json`, `.mcp.json`, `.agents/`, and
   `.claude/commands/dumpster-{create,hunt,launch}.md` all exist and are git-tracked. Cases in section A read this
   checked-in state; they do not need a rebuild unless the case says so.
2. To watch `init` actually WRITE something in this repo, re-run it: `npm run build && npm link --workspaces && npm
   run init` (root `CLAUDE.md`, "Regenerating `.claude/settings.json` Here"). `git status --porcelain .claude .mcp.json
   .agents AGENTS.md .gitignore .dungeonmaster-assets` before and after each case in section B to see the real diff —
   most of it should be EMPTY, because re-running `init` on an already-initialized repo is designed to be a no-op or
   an additive merge, never a silent overwrite.
3. **Fresh consumer repo, built in `/tmp` (never `<repoRoot>/tmp` — this is a simulated EXTERNAL repo, not a scratch
   file of this checkout):**
   ```bash
   mkdir -p /tmp/dm-consumer-local && cd /tmp/dm-consumer-local
   npm init -y
   npm install /home/brutus-home/projects/codex-of-consentient-craft --no-save   # local tarball-equivalent install
   npx dungeonmaster init
   ```
   This gives Scenario 3 (local `node_modules`). For Scenario 4 (global-only), instead:
   ```bash
   cd /home/brutus-home/projects/codex-of-consentient-craft && npm pack --pack-destination /tmp
   npm install -g /tmp/dungeonmaster-*.tgz
   mkdir -p /tmp/dm-consumer-global && cd /tmp/dm-consumer-global
   npm init -y
   dungeonmaster init
   ```
   Clean up after: `rm -rf /tmp/dm-consumer-local /tmp/dm-consumer-global /tmp/dungeonmaster-*.tgz && npm uninstall -g dungeonmaster`.
4. A build that touches `packages/mcp` kills the running MCP stdio child. After any build in section A/B, reconnect
   before the next MCP-tool case: `/mcp` → reconnect `dungeonmaster` (`packages/mcp/CLAUDE.md`, "`npm run build` kills
   the running MCP child").
5. Most `quest`-flow MCP tool cases need a real `questId`/`workItemId`. Either walk feature 01/02's siegelense/
   hydration-recipe setup first to get a seeded quest, or create one live with `create-quest` (IN case below) and use
   its returned id for the rest of section I.
6. `dungeonmaster start` / `npm run prod` / `npm run dev` cases bind real ports (4800/4750/4751 in this repo's
   `.dungeonmaster.json`). Confirm nothing else in this session already has them open (`lsof -i :4800` etc.) before
   running one, and kill it at the end of the case.
