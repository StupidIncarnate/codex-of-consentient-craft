# Round C — composing the chainables (`recipes-chunk-12-combinatorial-rounds.md`, §8)

Every one of C1–C19 is DRIVEN this round — built and run against real framework code (never read and
predicted), staying at tiers 1–3 (the chain alone, the type fixtures, a file target with a temp home) per
this round's own instructions. Outcomes use the plan's own §5 vocabulary (`RULE`, `OBSERVABLE`,
`CONFIRMED`, `BLOCKED`) exactly. Every scratch script lives under `<repoRoot>/tmp/round-c/`, run via
`npx tsx --conditions=source tmp/round-c/<file>.ts` from the repo root; every quoted line below is copied
verbatim from a real run, not reconstructed from reading source. Where a case is fully answered by
reading a shipped file directly (tier 0), the file and line are cited and the answer is still confirmed
by a run wherever a run is possible at all.

**The recently-fixed `fromSaved` pre-flight check does not bear on any case below.**
`HydrationSavedFieldMissingError` (`packages/hydration/src/errors/hydration-saved-field-missing/`) fires
only when a `fromSaved({field})` names a field the PRODUCING ingredient's own `record` contract never
declares. Read directly at `packages/hydration/src/brokers/plan/preflight/plan-preflight-broker.ts:132-151`
(the FROMSAVED check, step 2 of 5) — it fires on a missing FIELD, never on which of several rows a
repeated `saveRecordAs` NAME ends up holding (C3, C11, C12) and never on a verb targeting an already-
removed ref (C18). None of Round C's cases exercise it.

## Findings this round adds beyond what the plan already predicted

- **C19 is the worst finding in this round.** It is not merely "the chain refuses `filter().add()` but the op contract does not" (already known). The RUNNER's own nested-create branch in `op-filter-apply-layer-broker.ts` resolves routes off the enclosing `filter` op's ingredient, completely ignoring the nested `create` op's own `ingredient` field — a live misrouting bug, silent, reachable the moment any hand-built plan (or a future `include()`) puts a `create` inside a `filter`. Pre-flight checks the RIGHT ingredient; the walk runs the WRONG one's routes. Nothing in `siegelense-recipes.md` or any chunk plan names this.
- **C13 shows a CONFIRM-shaped case that does not fully hold**, in the same spirit as Round A's A16. `HydrationFilterExpectationError` DOES throw on an over-match, but Part 6's own rule ("ambiguity THROWS, and the error carries the candidates") is only half met: the class is structurally incapable of naming the candidates — it accepts only a count, and the one call site that could pass the matched records instead discards them.
- **C10 and C9 both close cases the plan's own text still frames as open or as needing a heavier tier.** C10's collision risk is closed by construction (`rowRefStatics.slot.matchWord`), the same pattern B6/B7 found for `callIndex`. C9 needs no run, no server and no chunk 7/8 ingredient at all — `planMakesTransformer` answers it from a hand-chained op tree alone, at tier 1.
- **C14 and C15 are one precedence rule, not two.** `defaults(index)` beats `under()` beats an ancestor link, entirely because of one spread order (`{...under, ...defaults}` at create-op build time) composed with one skip rule (`link-values-transformer.ts`'s "already in `ownFields`" check). Nothing in `siegelense-recipes.md` states this chain today.
- **C18's two sub-cases diverge in a way worth stating precisely.** A transition `set()` after `remove()` fabricates an in-memory "ghost" record with no `id`, never touching disk. A plain-field `set()` after `remove()` is silently reordered by `planFoldWritesTransformer` into the CREATE itself — the row is born already carrying the "later" field, then removed. Both are real, and they are different failure shapes for what reads like the same mistake at the call site.
- **C7's third reading is real, not hypothetical.** Two siblings linking to the same parent under one `add` normally resolve identically (same value, declaration order) — but if anything mutates the parent's OWN record entry between them (a transition `set`, which writes back to the row's real ref), the two siblings can resolve to two different values for what looks like one link.
