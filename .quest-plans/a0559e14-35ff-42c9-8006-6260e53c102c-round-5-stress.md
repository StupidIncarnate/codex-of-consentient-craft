**Deterministic widget test (new, green):**

### Point 3 — Resume when guild path is NOT a valid git repo — PASS, real gap found

**Live drive (`r5-stress-2`, before its crash):** bare guild directory (no `git init`, no
`.dungeonmaster.json`), one `in_progress` row ~30s old. Paused (confirmed `PENDING` + `present:false`).
Called resume — returned a clean `{"resumed":true,"restoredStatus":"in_progress","dispatch":{"started":true}}`,
no error surfaced. A follow-up `GET` showed the quest had already reached `status:"blocked"` / work item
`"failed"` (retryCount:3, orphan-recovery budget exhausted) within seconds — not a *persistent* ghost, only
because four real spawn attempts burned the retry budget fast in this environment.

**Root cause traced from source:** `questRepoRootBroker`'s ancestor walk-up, on a guild path with no
`.dungeonmaster.json` of its own, does not verify the ancestor it eventually finds actually belongs to the
guild — it just trusts the first hit climbing up, which in this run landed on an unrelated repo entirely.
`spawn-batch-layer-broker.ts` pre-stamps the work item `in_progress` + a fresh `startedAt`
UNCONDITIONALLY (only a `missing-worktree` result is refused) before the spawn is ever attempted — so the
row goes live and ticking against a resolved cwd that was never verified to be the guild's own directory.
In a real environment where that escaped ancestor's `devCommand` doesn't fail fast (unlike the fake CLI
here), this is a live, ticking, "healthy-looking" row running against the wrong repository indefinitely,
not merely a fast-failing one.

**RED:** `packages/orchestrator/src/brokers/quest/repo-root/quest-repo-root-broker.test.ts` — added
`"EDGE: {cwdResolveBroker resolves to an ancestor above the guild path, not the guild path itself} =>
falls back to the guild path instead of trusting the escaped ancestor"`.
`npm run ward -- --only unit -- packages/orchestrator/src/brokers/quest/repo-root/quest-repo-root-broker.test.ts`
→ FAIL exactly as expected: `Expected: "/home/testuser/my-guild", Received: "/some/unrelated/ancestor/repo"`.

**NEXT:** rework — `questRepoRootBroker`/`questCwdResolveBroker` needs to verify a resolved ancestor
actually corresponds to the guild before trusting it, mirroring the existing fallback-to-`guild.path`
behavior it already has for an outright `cwdResolveBroker` rejection. Out of scope to fix here (test-only).

### Point 4 — Pause → resume → pause again — PASS, real gap found (falsifies the design decision)

**Source trace (no live repro possible — see crash note above; this was reconstructed from code, then
proven with a deterministic broker test):**
- `orchestration-resume-responder.ts` flips quest status synchronously, then fires
  `questOrchestrationLoopBroker` fire-and-forget, never awaited.
- `quest-resume-responder.ts` (server) additionally calls `orchestratorPlayDispatchAdapter({})` — only
  flips an in-memory flag; the real Node dispatch-loop kick is a fire-and-forget `.catch()` in
  `quest-node-dispatch-runner-broker.ts`, also never awaited by the HTTP response.
- The actual re-stamp (`in_progress` + fresh `startedAt`) happens in
  `spawn-batch-layer-broker.ts:85-99` ("Pre-stamp BEFORE spawning"), fully decoupled from the resume
  request/response cycle — confirming resume's HTTP response and the real re-stamp are genuinely
  asynchronous and unordered relative to each other.
- `quest-pause-broker.ts` decides which work items count as "active" from an UN-LOCKED `questGetBroker`
  read, taken BEFORE it calls the locked `questModifyBroker` (`quest-with-modify-lock-broker.ts` only
  serializes the write, not the read that decided what to write).

**RED (deterministic, not flaky):**
`packages/orchestrator/src/brokers/quest/pause/quest-pause-broker.integration.test.ts` (same file as
point 1's test), new case `"VALID: {an immediate second pause races the resumed dispatch's async
re-stamp} => ..."`. `npm run ward -- -- packages/orchestrator/src/brokers/quest/pause/quest-pause-broker.integration.test.ts`
→ lint PASS, typecheck PASS, integration FAIL:
```
-   "startedAt": undefined,       +   "startedAt": "2026-09-09T12:16:43.383Z",
-   "status": "pending",          +   "status": "in_progress",
```
`questPauseBroker` itself reported `{paused:true}` and the quest read `paused` — but the work item
survived the pause fully `in_progress` with a FRESH `startedAt`: an orphaned "ghost running" row, ticking a
live duration, that no pause ever caught, and indistinguishable in the UI from a legitimately running row
(`execution-row-layer-widget.tsx`'s `isRunning` reads only the work item's own status, never the quest's).
Deterministic because both racing calls are synchronous function invocations whose program order
guarantees the outcome. **This directly falsifies `#pause-costs-no-new-field`'s claim that pause always
catches every active item** — distinct from point 1's double-pause race, in the same test file, also still
failing (pre-existing, not introduced by this point).

**NEXT:** rework — fix belongs in `quest-pause-broker.ts`: the "which items are active" decision must be
re-taken from a quest snapshot read INSIDE the same per-quest lock the write goes through, mirroring the
orphan-reset race fix already documented in `playbook/e2e-flakiness-log.md`'s 2026-08-09 entry. Not
applied — out of scope (test-only).

**Note on the mid-task crash**: `r5-stress-2` stopped responding (curl + raw socket connect both refused,
on both apiPort and webPort) partway through this point's live-repro attempt, ~7 minutes after its last
log line — well inside the 15-minute idle timeout and not attributable to idle closure. Neither sub-agent
killed it. Left as an open, uninvestigated infra question; `r5-stress-3` was booted immediately after.
