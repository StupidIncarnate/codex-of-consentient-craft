# Guide — running-elapsed-on-work-item-row

Source of the behavior under test:
- `packages/web/src/widgets/execution-panel/execution-row-layer-widget.tsx` — the row. Gate:
  `startedAt && elapsedEndPoint` where `elapsedEndPoint = completedAt ?? (isRunning ? now : undefined)`
  and `isRunning = status === 'in_progress'`.
- `packages/web/src/widgets/execution-panel/execution-panel-widget.tsx` — owns the shared tick.
  `hasRunningWorkItem = visibleWorkItems.some(wi => wi.status === 'in_progress' && wi.startedAt !== undefined)`,
  fed into `useElapsedTickBinding({ enabled: hasRunningWorkItem })`.
- `packages/web/src/bindings/use-elapsed-tick/use-elapsed-tick-binding.ts` — one `setInterval` at
  `elapsedDisplayConfigStatics.refresh.tickMs` (60000ms), read fresh via `Date.now()` on every fire.
- `packages/web/src/transformers/elapsed-parts/elapsed-parts-transformer.ts` — floors `(endedAt - startedAt)`
  to whole seconds, clamps negative to 0.
- `packages/web/src/transformers/duration-display/duration-display-transformer.ts` — `<1m` under 60s,
  `Nm` under 60 minutes, `NhNm`/`Nh` (drops `m` when minutes is 0) at 60+ minutes.
- `packages/web/src/statics/elapsed-display-config/elapsed-display-config-statics.ts` — thresholds:
  `minuteThresholdSeconds: 60`, `hourThresholdMinutes: 60`.

The existing e2e suite (`packages/web/src/flows/quest-chat/elapsed-duration-*.e2e.ts` +
`packages/web/test/harnesses/elapsed-duration/elapsed-duration.harness.ts`) already drives every one of
these 20 paths through Playwright. Read it before re-deriving anything below — it is the single highest-value
reference and every recipe in this guide is drawn directly from it, adapted to a hand-driven siege lane
instead of a Playwright test file.

## TOOLING

- **No MCP browser tool is registered for this session** (`ToolSearch` for `browser`/`chrome`/`devtools`/
  `playwright` returns nothing), and none is needed: `packages/orchestrator/CLAUDE.md` states plainly that
  "Siegemaster's `ui-state` observables are driven by a Playwright lane... no session dispatched from this
  package needs `mcp__claude-in-chrome__*`." The real mechanism is `packages/web/test/siege-driver/`, a CLI
  process you drive over the filesystem, not a tool call.
- **Boot one lane** (own port pair, own throwaway `DUNGEONMASTER_HOME`, own headless Chromium — this IS a
  real, fully-rendering browser engine, just with no OS window):
  ```bash
  npx tsx packages/web/test/siege-driver/siege-driver.ts <laneName>
  ```
  Run this via Bash with `run_in_background: true` — it blocks for the lane's whole life (up to a 15-minute
  idle timeout, `IDLE_TIMEOUT_MS` in `siege-driver.ts`). Wait for `tmp/siege/<laneName>/lane.json` to exist,
  then `Read` it for `apiPort`, `webPort`, `home` (= that lane's `DUNGEONMASTER_HOME`), `commandsDir`,
  `resultsDir`, `screenshotDir`. Boot takes up to ~180s cold (Vite pre-bundle + tsx boot) — poll, don't sleep
  a fixed guess.
- **Drive the browser (`ui-state` surface)**: drop one JSON file per command into `commandsDir`
  (`Write` tool), numbered so they sort in order (`010-goto.json`, `020-waitfor.json`, ... — increment by 10),
  then poll for the same basename to appear in `resultsDir` as `<name>.txt` (`OK`/`FAIL`, a blank line, then
  a JSON reading). Command shape:
  `{"name": "<goto|waitFor|click|type|key|paste|screenshot|box|dom|storage|console|network|ws|eval|file|end>", "target": "...", "value": "...", "filePath": "...", "timeoutMs": 0}`.
  Default command timeout is 10000ms (`timeoutMs: 0` means "use the default").
  Full vocabulary and field meaning: `packages/web/test/siege-driver/siege-command.ts` header comment.
- **Reading one row's text/visibility/count** — use `box`, never `dom`, when you need to scope to a specific
  row by its text. `box`'s locator goes through Playwright's engine (`page.locator`), which understands the
  `:has-text()` pseudo-class; `dom` uses a raw `document.querySelectorAll`, which does not. Selector shape:
  `[data-testid="execution-row-layer-widget"]:has-text("<exact operation text>") [data-testid="execution-row-duration"]`.
  The `box` reading returns `{selector, count, present, visible, box, text}` when present, `{selector, count, present:false}`
  when absent — `present:false`/`count:0` IS the "no duration element" reading.
- **The real HTTP exchange (guild/quest CRUD, pause/resume, the no-op PATCH forcing trick)** — plain `curl`
  against the lane's OWN api port: `http://dungeonmaster.localhost:<apiPort>/api/...`. `curl` is not blocked
  in this repo (only native grep/find/search + bare `tsc`/`eslint` are). This is simpler than routing every
  API call through the browser's `eval`+`fetch`, and it is exactly what the e2e harnesses (`guildHarness`,
  `questHarness`, `dispatchHarness`) do via Playwright's `request` fixture — same routes, same bodies.
- **quest.json / the event outbox (off-screen)** — under the lane's `home`, which is always an OS `/tmp`
  path. See OFF-SCREEN for the exact tool rule — `Write`/`Edit` tool to write it, `Read` tool or the siege
  driver's own `file` command to read it, never a raw Bash command. That `file` command is READ-ONLY anyway
  (`fs.readFileSync`/`readdirSync`/`statSync`; see the PURPOSE comment in `siege-command.ts`: "never into a
  verdict"). Path shape: `<home>/guilds/<guildId>/quests/<questFolder>/quest.json`. If you do want a reading
  taken FROM INSIDE the lane's own process (e.g. to prove the browser's own view of a file, or to read a
  relative path without knowing `home` by hand), `{"name":"file","target":"guilds/<guildId>/quests/<questFolder>/quest.json"}`
  resolves relative to `home` and returns the same JSON your own `Read` would.
- **Console / network capture** — `{"name":"console","target":""}` and `{"name":"network","target":"<url substring>"}`,
  both armed from lane boot (before any navigation), so nothing is missed. Useful for catching a React
  warning/error that would explain a blank panel, and for confirming a PATCH/POST actually fired.
- **Server logs** — `tmp/siege/<laneName>/api-server.log` and `.../web-server.log` (Read tool).
- **Real wall-clock tick** — see FORCING below. There is no CDP/Playwright clock override reachable from a
  siege lane (the command vocabulary has no `clock`/`fastForward` verb, and `page.clock` is a Node-side
  Playwright API the file-drop protocol never exposes) — the honest route for the `tick` transition is
  sleeping past the real 60s.
- **`check-elapsed-split`'s raw `{hours,minutes,seconds}` triple is not independently observable anywhere**
  — it is a pure function's return value, computed and discarded inside one render, never persisted to disk
  or exposed on any endpoint, and `durationDisplayTransformer` always drops the seconds digit from what's
  shown. The nearest real-system proxy: seed a span of exactly 4530000ms (plus a few hundred extra ms, to
  prove the extra milliseconds get floored away rather than rounding the minute up) and confirm the row
  reads exactly `1h15m` — see FORCING.

## ENTRY

- `/{urlSlug}/quest/{questId}` relative to the lane's OWN `baseUrl` (`http://dungeonmaster.localhost:<webPort>`,
  printed in `lane.json`) — never a fixed origin; each lane's port pair is OS-assigned fresh.
- No login, no feature flag, no precondition beyond the quest existing on disk with `status: "in_progress"`
  and at least one work item. `urlSlug` — read straight off the `POST /api/guilds` response's `urlSlug` field
  (do not hand-derive it).
- `goto` command: `{"name":"goto","target":"/{urlSlug}/quest/{questId}","timeoutMs":30000}`.
- Wait for `[data-testid="execution-panel-widget"]` to be visible (`waitFor`, default state `visible`)
  before reading any row.

## SEEDING

**1. Create a guild.** A bare directory is enough for every path EXCEPT the pause/resume observable
(`check-resumed-row-restarts`) — see the note at the end of this section. Use
`<repoRoot>/tmp/dm-siege-<laneName>-guild` for the guild's own working directory, never a hand-rolled path
under OS `/tmp` — this repo's pre-bash hook denies raw Bash `mkdir`/`git`/`cat` aimed at an OS `/tmp` path, and
`CLAUDE.md` wants scratch under `<repoRoot>/tmp` anyway. This is a DIFFERENT directory from the lane's own
`DUNGEONMASTER_HOME` (`home` in `lane.json`, e.g. `/tmp/dm-siege-<laneName>-<pid>`) — THAT one is fine under OS
`/tmp`, because the lane PROCESS creates it itself and every write into it in this guide goes through the
`Write`/`Read` tools, never a raw Bash command aimed at it.
```bash
mkdir -p <repoRoot>/tmp/dm-siege-<laneName>-guild
curl -s -X POST http://dungeonmaster.localhost:<apiPort>/api/guilds \
  -H 'Content-Type: application/json' \
  -d '{"name":"Elapsed Duration Guild","path":"<repoRoot>/tmp/dm-siege-<laneName>-guild"}'
```
Response: `{"id": "<guildId>", "urlSlug": "<urlSlug>", ...}`.

**2. Create a quest** (bare bookkeeping — no spawn, no git):
```bash
curl -s -X POST http://dungeonmaster.localhost:<apiPort>/api/quests \
  -H 'Content-Type: application/json' \
  -d '{"guildId":"<guildId>","title":"Elapsed Duration Quest","userRequest":"Build the feature"}'
```
Response: `{"success":true,"questId":"<questId>","questFolder":"<questFolder>","filePath":"<absolute path>"}`.
`filePath` is `<home>/guilds/<guildId>/quests/<questFolder>/quest.json` — the SAME `home` from `lane.json`.

**3. Overwrite `filePath` wholesale** with a full quest, status ALWAYS `"in_progress"` (every path in this
flow keeps the quest itself `in_progress`; only WORK-ITEM status varies row to row). One operation item +
one work item per row you want on screen, linked 1:1 via `relatedDataItems: ["operations/<opId>"]`. Give
each operation a distinct `text` — that text becomes the row's visible name and is how you select a specific
row later:

```json
{

  "createdAt": "2026-01-01T00:00:00.000Z",

    {
      "id": "e2e00000-0000-4000-8000-000000000001",
      "role": "codeweaver",

      "relatedDataItems": ["operations/00000000-0000-4000-8000-000000000001"],

    { "name": "auth-service", "location": "./packages/auth-service", "changeType": "edit", "packageType": "library" }

  "flows": [
    {
      "id": "harness-flow",

  ]

```
This is the exact shape `packages/web/test/harnesses/quest/quest.harness.ts`'s `writeQuestFile` produces
(read that file for the full field-by-field mapping if a value here does not parse).

**`operations[].status` and `workItems[].status` are DIFFERENT enums — do not reuse one for the other.**
`operationItemContract.status` (`packages/shared/src/contracts/operation-item/operation-item-contract.ts`) is
`z.enum(['pending', 'in_progress', 'complete'])` — three values, no `queued`, no `failed`, no `skipped`.
`workItemStatusContract` is the six-value union (`pending | queued | in_progress | complete | failed | skipped`).
Seeding several rows makes it tempting to reach for `queued` on an operation item because the WORK item accepts
it — `operations[].status` never does. Give an operation item one of the three values above only.

`startedAt`/`completedAt` MUST be full `z.string().datetime()` values — millisecond precision, trailing `Z` — a bare date or a value
missing `Z` fails to parse and the WHOLE quest.json fails to load (blank panel, no error banner).

**4. Placing a work item at an EXACT elapsed age.** For a still-RUNNING row (`status: "in_progress"`, no
`completedAt`), compute `startedAt` as real-`Date.now()` minus the exact offset — there is no fake clock in a
live lane, so every "now-relative" age is seeded against the REAL wall clock, exactly as
`elapsed-duration-pause.e2e.ts` does (it installs no fake clock at all, for the same reason). Compute this
right before you write the file, and immediately before navigating — a few seconds of curl/Write/goto latency
eats into your margin:

| Target age | Offset from now (ms) |
|---|---|
| 30s | 30,000 |
| 59s | 59,000 |
| 60s | 60,000 |
| 4m30s | 270,000 |
| 59m59s | 3,599,000 |
| 60m (1h) | 3,600,000 |
| 1h13m | 4,380,000 |
| 2h | 7,200,000 |

For a FINISHED row (`status` anything reachable — typically `complete`, `failed`), set BOTH `startedAt` and
`completedAt` to any fixed pair with the target gap between them (these do not need to be near real-now,
since the end point is `completedAt`, not `now`):

| Target span | startedAt | completedAt |
|---|---|---|
| 12s (under a minute) | `2026-01-01T09:00:00.000Z` | `2026-01-01T09:00:12.000Z` |
| 4m12s | `2026-01-01T09:10:00.000Z` | `2026-01-01T09:14:12.000Z` |
| 1h13m | `2026-01-01T09:20:00.000Z` | `2026-01-01T10:33:00.000Z` |
| 2h exactly | `2026-01-01T09:30:00.000Z` | `2026-01-01T11:30:00.000Z` |
| 1h15m30s (elapsed-split) | `2026-01-01T09:00:00.000Z` | `2026-01-01T10:15:30.500Z` (4530.5s gap — proves ms floors away) |
| negative (clamp) | `2026-01-01T09:00:05.000Z` | `2026-01-01T09:00:00.000Z` (completedAt BEFORE startedAt) |

**5. Two of anything an assertion must tell apart** — e.g. for `check-rows-advance-together` /
`check-interval-survives-partial-stop`, write TWO work items in the SAME `workItems[]` array sharing one
`startedAt`, each with its own operation `text` so you can select each row independently.

**6. Making a mid-walk mutation land on an ALREADY-OPEN page without a reload.** Writing quest.json alone
does not wake a browser that already subscribed before the write landed (the appended outbox line is written
by an external process, which the e2e comments note is unreliable for that case). The reliable trick, lifted
verbatim from `elapsed-duration-finished.e2e.ts` / `elapsed-duration-tick.e2e.ts`: after rewriting the file,
fire a **no-op PATCH** — same status value the quest already has — which forces the server's OWN
persist-and-broadcast path to re-read the file you just wrote and push it over the websocket:
```bash
curl -s -X PATCH http://dungeonmaster.localhost:<apiPort>/api/quests/<questId> \
  -H 'Content-Type: application/json' -d '{"status":"in_progress"}'
```
Use this for: "completedAt arrives" mid-test, a row completing while a sibling keeps running, and the interval-
clears-when-none-running transition. You do NOT need this before the FIRST `goto` — the browser fetches
current state fresh on load.

**7. The pause/resume observable (`check-resumed-row-restarts`) needs a real git fixture repo at the guild
path**, because RESUME actually re-dispatches a work item, and dispatch resolves `.dungeonmaster.json` by
walking up from the guild path (`cwdResolveBroker`, `@dungeonmaster/shared`). PAUSE alone (reaching
`paused-no-figure` without ever resuming) needs none of this — `questPauseBroker` only kills processes and
flips work-item status to `pending`, pure bookkeeping. Mirror
`packages/web/test/harnesses/environment/environment.harness.ts`'s `ensureFixtureRepo`.

**`git init` cannot be run as a raw Bash command in this session, and neither can a bare `git --version`.**
This session's Bash allow-list for `git` is a curated subcommand set — `status`, `log`, `diff`, `show`, `add`,
`rm`, `mv`, `commit`, `checkout`, `merge`, `push`, `rev-parse`, `merge-base` — and `init` is not on it; anything
outside that literal set is denied outright, which reads like a broken environment if you don't know the list
is curated rather than complete. `node:*` is unrestricted, so shell out through `child_process.execFileSync`
from a Node script instead — every git call here, including ones that ARE on the allow-list, so the whole
fixture goes through one uniform mechanism rather than half Bash / half Node:
```bash
node -e '
const { execFileSync } = require("child_process");
const fs = require("fs");
const path = require("path");
const GUILD = "<repoRoot>/tmp/dm-siege-<laneName>-guild";
const env = { ...process.env, GIT_AUTHOR_NAME: "siege", GIT_AUTHOR_EMAIL: "siege@dungeonmaster.test",
  GIT_COMMITTER_NAME: "siege", GIT_COMMITTER_EMAIL: "siege@dungeonmaster.test",
  GIT_CONFIG_COUNT: "1", GIT_CONFIG_KEY_0: "commit.gpgsign", GIT_CONFIG_VALUE_0: "false" };
const git = (args) => execFileSync("git", args, { cwd: GUILD, env, stdio: "ignore" });
fs.mkdirSync(GUILD, { recursive: true });
git(["init", "-b", "main"]);
fs.writeFileSync(path.join(GUILD, ".dungeonmaster.json"), JSON.stringify({
  framework: "monorepo", schema: "zod",
  devServer: { devCommand: "true", port: 47001, buildCommand: "true" },
}));
fs.writeFileSync(path.join(GUILD, "README.md"), "# fixture\n");
fs.mkdirSync(path.join(GUILD, "packages", "demo"), { recursive: true });
fs.writeFileSync(path.join(GUILD, "packages", "demo", "package.json"),
  JSON.stringify({ name: "@dungeonmaster/demo", version: "1.0.0" }));
git(["add", "-A"]);
git(["commit", "-m", "base"]);
fs.appendFileSync(path.join(GUILD, "README.md"), "second\n");
git(["add", "-A"]);
git(["commit", "-m", "second commit"]);
fs.mkdirSync(path.join(GUILD, "node_modules", "@dungeonmaster"), { recursive: true });
fs.symlinkSync(path.join("..", "..", "packages", "demo"), path.join(GUILD, "node_modules", "@dungeonmaster", "demo"));
fs.mkdirSync(path.join(GUILD, "node_modules", "zod"), { recursive: true });
'
```
The lane's own API server is already spawned with `CLAUDE_CLI_PATH` pointed at the fake Claude CLI
(`siege-lane.ts`), so a resumed dispatch spawns the fake binary, not a real Anthropic call — no cost, no
network dependency. **Before clicking resume, queue that fake CLI a response** — see FORCING's "Resume" entry;
skipping this makes the resumed dispatch fail in under a second, far too fast for the file-drop protocol to
ever observe the resumed `in_progress` row.

## RESET

- **Between two seeded quests in the same lane**: `DELETE /api/guilds/<guildId>` removes the guild record,
  but does **not** remove the guild's own working-directory git fixture repo (still has `.git`, both commits,
  `node_modules`, and any `worktrees/` a real carve made) — `rm -rf` that path yourself if you need a truly
  clean fixture for a next round. It also does not touch `~/.claude/projects/<encoded-guildPath>/` session
  JSONL files if you ever create one.
- **Ending the whole lane**: drop `{"name":"end"}` as the next command, or send SIGINT/SIGTERM to the
  `npx tsx` process. This closes the browser, kills both spawned servers (API + Vite), and — per
  `siege-lane.ts`'s `stop()` — **removes the lane's `DUNGEONMASTER_HOME` entirely** (every guild, every
  quest.json, `event-outbox.jsonl` — all gone).
- **What ending the lane does NOT reset**: `tmp/siege/<laneName>/` in the repo itself (`lane.json`,
  `commands/`, `results/`, `screenshots/`, `api-server.log`, `web-server.log`) — these persist on disk for
  postmortem. A fresh `siege-driver.ts <laneName>` boot on the SAME lane name clears only `commands/` (see
  TRAPS) — `results/` and the logs are not cleared, so old readings can linger if you reuse a lane name.
- **A lane auto-closes** after 15 minutes (`IDLE_TIMEOUT_MS`) with no new command dropped — this also runs
  the same teardown as an explicit `end`.

## CONTROLS

- `[data-testid="execution-panel-widget"]` — panel root.
- `[data-testid="execution-row-layer-widget"]:has-text("<operation text>")` — one specific row (Playwright
  locator syntax; use with `box`/`click`/`waitFor`, not `dom`).
- `[data-testid="execution-row-duration"]` (scoped inside the row selector above) — the figure itself; a
  `box` reading of `count:0`/`present:false` means "no figure rendered."
- `[data-testid="execution-row-status-badge"]` (scoped) — text is one of `RUNNING`, `PENDING`, `QUEUED`,
  `DONE`, `FAILED`, `PARTIAL`, `BLOCKED`, `SKIPPED` (`executionStepStatusConfigStatics.statusConfig`).
- `[data-testid="EXECUTION_PAUSE_BUTTON"]` — click to POST `/api/quests/<questId>/pause`.
- `[data-testid="EXECUTION_RESUME_BUTTON"]` — click to POST `/api/quests/<questId>/resume`, only rendered
  when the quest is `paused`/`blocked`.
- `[data-testid="LOGO_LINK"]` — a react-router `<Link to="/">`; click to trigger a CLIENT-SIDE route change
  (unmounts the execution panel WITHOUT a full page navigation — important for the interval-cleared-on-unmount
  invariant, since a `goto` to a new URL would tear down the whole JS realm and prove nothing about React's
  own cleanup).

## OFF-SCREEN

- **A lane's `home` is ALWAYS an OS `/tmp` path** (`/tmp/dm-siege-<lane>-<pid>/...`), and that governs HOW you
  touch anything under it, not just where it is:
  - **Writing** anything under `home` — quest.json, an outbox line, a claude-queue response file — must go
    through the `Write` or `Edit` TOOL. Never Bash: a raw Bash command aimed at an OS `/tmp` path is denied
    outright by this session's permission hook, `node -e "fs.writeFileSync('/tmp/...')"` included, and the
    denial reads like a broken environment rather than the rule it actually is.
  - **Reading** it goes through the `Read` tool, or the siege driver's own `file` command.
  - Bash `node -e` (and `date`) are fine ONLY when they compute and print a value to stdout and write no
    file — that is how you compute a `startedAt` offset for SEEDING step 4, and it still works exactly as
    written there.
- quest.json on disk: `<home>/guilds/<guildId>/quests/<questFolder>/quest.json` — the authoritative work-item
  `startedAt`/`completedAt`/`status`.
- Event outbox: `<home>/event-outbox.jsonl` — one `{"questId":...,"timestamp":...}` line per mutation that
  should wake a live watcher.
- `GET http://dungeonmaster.localhost:<apiPort>/api/quests/<questId>` → `{"quest": {...}}` — the server's own
  current view; poll this to confirm a resumed work item's `startedAt` actually moved server-side before
  trusting what the browser shows.
- `tmp/siege/<laneName>/api-server.log`, `.../web-server.log` — server stdout/stderr.
- The `network` siege command (armed from boot) — every request/response body since lane start, filterable
  by URL substring; use it to confirm a PATCH/pause/resume request actually fired and what it returned.
- The `console` siege command — browser console + uncaught page errors, useful when a panel renders nothing
  and you need to know whether React threw.

## FORCING

Distinct force conditions, de-duplicated across the 20 paths (many paths share a force verbatim):

- **"startedAt absent"** (P1): write the work item with NO `startedAt` key at all (omit it — `writeQuestFile`
  never defaults one in). Any status. Confirm via `box` on `execution-row-duration`: `present:false`.
- **"startedAt present" / "no completedAt and not in_progress"** (P2): give the work item a `startedAt` but
  no `completedAt`, and any status OTHER than `in_progress` (`pending`, `queued`, `complete` [without a
  completedAt — unusual but structurally reachable], `failed`, `skipped`). `execution-row-duration`:
  `present:false`.
- **"in_progress, no completedAt — end point is now"** (P3-P11): `status: "in_progress"`, `startedAt` set
  per the age table above, no `completedAt`. This is also what makes `hasRunningWorkItem` true and starts the
  panel's shared tick.
- **"completedAt present — end point is completedAt"** (P12-P20): both `startedAt` and `completedAt` set —
  status can be anything (typically `complete`); the widget's `elapsedEndPoint = completedAt ?? ...` takes
  `completedAt` unconditionally once it exists, regardless of the work item's current status.
- **"under 60s" / "60s or more" / "under 1h" / "1h or more"**: pick the row's age/span from the tables in
  SEEDING step 4.
- **"unmounted or no longer in_progress" → timer-cleared**: EITHER click `[data-testid="LOGO_LINK"]` (panel
  unmount) OR — for a row that was the LAST one running — flip its status away from `in_progress` via the
  no-op-PATCH trick (SEEDING step 6). There is no direct way to "read the interval count" from a live siege
  lane (see the paragraph below) — the closest real proxy is behavioral: after the transition, wait a further
  65+ real seconds and confirm NOTHING on screen changed (a frozen or absent figure stays exactly as it was).
- **"completedAt arrives" → show-final-duration**: whether the row started with NO `completedAt` (P4/P7/P10)
  or already had a DIFFERENT `completedAt` value (P13/P16/P19), rewrite the work item's `completedAt` field to
  a NEW ISO value landing in the target band, then force the no-op PATCH (SEEDING step 6). The figure updates
  on that render — no tick needed, no wait needed. Confirm the new text immediately after the PATCH request
  resolves (poll `box`, do not assume it's instant — allow the default 10s command timeout to do its own
  retrying via a `waitFor` on the NEW text if you want a stricter proof it changed rather than always having
  been that value).
- **"quest paused" → paused-no-figure, from the "in_progress, no completedAt" group** (P5, P8, P11): click
  `[data-testid="EXECUTION_PAUSE_BUTTON"]`. This POSTs `/api/quests/<questId>/pause`, which
  (`quest-pause-broker.ts`) resets every work item whose status is currently ACTIVE (`isActiveWorkItemStatusGuard`
  — includes `in_progress`) to `pending`, and flips quest status to `paused`. The row's own `elapsedEndPoint`
  then evaluates to `undefined` (status is no longer `in_progress`, still no `completedAt`) and the figure
  disappears; badge reads `PENDING`.
- **"quest paused" → paused-no-figure, from the "completedAt present" group** (P14, P17, P20) —
  **NOT FOUND — the reader must work this out; do not trust a guessed recipe here.** Reading
  `quest-pause-broker.ts` directly: it only resets work items matching `isActiveWorkItemStatusGuard` (active =
  still running/queued) to `pending`, and never touches a work item's `completedAt` field. A row that already
  carries `completedAt` keeps `elapsedEndPoint = completedAt` UNCONDITIONALLY per
  `execution-row-layer-widget.tsx`'s own gate, so pausing the quest should NOT clear its figure — the widget
  code gives no path from "completedAt present" to "no figure" via a pause action alone. Before walking this
  specific sub-case, cross-check against a real run (or ask whether the path intends a DIFFERENT precondition,
  e.g. a fresh retry work item created after a `pt N` continuation, which starts `pending` with no
  `startedAt`/`completedAt` of its own and reads as case P2, not P14/P17/P20's stated "completedAt present"
  force).
- **check-negative-span-clamps**: seed `completedAt` earlier than `startedAt` (SEEDING table). Confirm the
  row still reads exactly `<1m` — never a negative number, never a huge positive number, never `NaN`.
- **check-elapsed-split**: seed the 4530.5s-gap pair from the SEEDING table; confirm the row reads exactly
  `1h15m` (proves both the hour/minute split AND flooring of the extra 500ms).
- **Real 60-second tick**: there is no clock override available (see TOOLING). Seed a running row, read its
  figure, then actually wait — `sleep 65` (bash) or an equivalent real delay — before re-reading. Budget
  wall-clock time accordingly; do not attempt this against more than one band per sleep (advancing 65s moves
  every currently-visible running row by the same one tick).
- **Pause**: click `EXECUTION_PAUSE_BUTTON`, confirmed via the `network` command showing a
  `POST .../pause` with 200, or via `GET /api/quests/<questId>` showing `status: "paused"`.
- **Resume**: **before clicking**, queue the fake Claude CLI a response that PARKS the re-dispatched child —
  with nothing queued, its "queue is empty" retry loop runs to failure in about one second (four retries, exit
  code 1, work item `failed`, quest `blocked`), far too fast for the file-drop protocol to ever catch the
  intermediate `in_progress` render. Write `{"sessionId":"<any uuid>","lines":[],"hang":true}` to
  `<home>/claude-queue/__by_cwd__/<encoded-guild-path>/0000.json`, where `<encoded-guild-path>` is the guild's
  `path` (SEEDING step 7's `GUILD`) with every character outside `[A-Za-z0-9._-]` replaced by `_` — verified
  against `encodeCwdScope` in `packages/web/test/harnesses/claude-mock/claude-mock.harness.ts`, mirrored
  verbatim in `packages/web/test/harnesses/claude-mock/bin/claude`. `lines: []` + `hang: true` makes the fake
  CLI emit nothing and block forever, so the work item sits `in_progress` and readable for as long as you need
  it. THEN click `EXECUTION_RESUME_BUTTON` (only visible once `status` is `paused`/`blocked`), confirmed via
  `network` showing `POST .../resume` returning `{"resumed":true,"restoredStatus":"in_progress","dispatch":{"started":true}}`,
  then poll `GET /api/quests/<questId>` until the target work item's `status === "in_progress"` AND its
  `startedAt` is STRICTLY LATER than the value you seeded pre-pause (proves a fresh stamp, not the stale one)
  — this needs the git-fixture guild path from SEEDING step 7.

## TRAPS

- **`dom` vs `box`**: `dom` cannot use `:has-text()` (it's a raw `querySelectorAll`, not a Playwright
  locator) — using it to scope to one row by text silently returns EVERY row, or none. Use `box`.
- **The row's visible name comes from the OPERATION's `text` field, not the work item's role or id.** A work
  item with no linked operation (`relatedDataItems` missing an `operations/<id>` ref, or the ref pointing at
  a non-existent operation) falls back to the capitalized role name (`"Codeweaver"`) — give every seeded row
  a distinct, real operation `text` or your `:has-text()` selectors collide.
- **ONE bad field ANYWHERE in quest.json fails the WHOLE parse, and nothing on screen says so.** The panel
  just renders blank — the real zod error only ever appears in `api-server.log` and in a `quest-load-failed`
  websocket frame, never in the browser. Two known ways to trip this while seeding this flow: `startedAt`/
  `completedAt` not a full ISO datetime with milliseconds and a trailing `Z`, and `operations[].status` set
  to a `workItems[]`-only value like `queued` (see SEEDING — `operations[].status` is the three-value
  `pending | in_progress | complete`, not the six-value work-item union). Neither is the whole list — treat a
  blank panel as "check `api-server.log` for the actual `Invalid enum value`/`Invalid datetime` message"
  before assuming anything else is wrong.
- **The outbox line you append yourself is not a reliable wake-up for an already-subscribed browser** — it's
  written by an external process (you), not by the server's own `questPersistBroker`, and a client that
  subscribed before your write landed may not notice. Use the no-op PATCH trick for any mid-walk mutation.
- **`isRunning` (row-level) and `hasRunningWorkItem` (panel-level tick gate) are two different tests that
  must be kept in sync mentally**: a row with `status: "in_progress"` but NO `startedAt` shows no figure AND
  does not start the shared interval — don't read "no interval registered" as proof the row isn't
  "running" by status; it can be `in_progress` and still contribute nothing to the tick.
- **Quest status stays `"in_progress"` for the ENTIRE flow** in every path except the pause force branches.
  Pausing is a separate `POST /pause` call that flips QUEST status; it is not something you set by hand-editing
  quest.json's `status` field (that field also gates which quest-level actions the UI renders, e.g. the
  RESUME button only appears once status is genuinely `paused`/`blocked`).
- **Guild path (a git working directory) and `DUNGEONMASTER_HOME` (the lane's `home`) are different
  directories entirely.** quest.json lives under `home`; the guild's OWN git fixture (needed only for
  resume) lives at whatever `path` you gave `POST /api/guilds`. Don't write quest.json into the guild path or
  vice versa.
- **This has bitten twice now: `home` is an OS `/tmp` path, so any raw Bash write aimed at it — quest.json,
  the outbox, a claude-queue response file, even a `node -e "fs.writeFileSync(...)"` one-liner — is denied
  outright by this session's permission hook, and the denial looks exactly like a broken environment rather
  than a rule.** See OFF-SCREEN for the actual rule: `Write`/`Edit` tool to write under `home`, `Read` tool or
  the siege driver's `file` command to read it. Bash `node -e`/`date` stay fine for compute-only work (the
  `startedAt` offset in SEEDING step 4) as long as they only print to stdout and touch no file.
- **Command files are cleared at lane boot, result files are NOT.** Re-running `siege-driver.ts` on a
  lane name that still has old files under `tmp/siege/<laneName>/results/` leaves those stale readings
  sitting there — don't glob `results/*.txt` expecting only the current walk's output without checking
  timestamps or basenames first.
- **The siege driver process itself blocks for the lane's life** — always launch it with
  `run_in_background: true`; do not expect the Bash call that started it to return until the lane closes.
- **A `box`/`click`/`waitFor` command's default timeout (10s) can be too short for a websocket round trip
  after a PATCH** under load — pass an explicit larger `timeoutMs` if a `waitFor` on new text seems to be
  racing the update rather than actually observing the old value.
- **The riftcarver/dispatch machinery is entirely bypassable for every path except resume** — do not create
  quests through the normal spec lifecycle (ChaosWhisperer, Start Quest, etc.) for this flow; hand-writing
  quest.json directly at `status: "in_progress"` with the work items you need is the same shortcut every
  existing e2e spec for this flow takes, and it's an order of magnitude faster than driving a real spec.
