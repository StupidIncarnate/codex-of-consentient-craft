The design decision under test is `#single-shared-tick`: "One 60-second interval drives every
visible running row... so work does not climb per row." The existing units (`check-one-interval-
for-all-rows`, `check-rows-advance-together`, `check-interval-survives-partial-stop`, `check-
interval-cleared-when-none-running`) all prove their claims at 2-3 rows. Nothing in this quest
proves the claim holds at a realistic row count. Volume chosen for this round: **55 rows** (55
satisfies "try 50+"), used two ways below — as 55 running rows, and as a 50-finished + 5-running
mix that isolates whether recompute cost tracks RUNNING rows or TOTAL panel size.

   present, ages spread under 60s, no completedAt) on one panel. Drive the real lane: `goto` the
   quest page, then use the armed `network` command to count requests fired by that ONE navigation,
   and time (via `waitFor` polling / repeated `box` reads) how long it takes for the LAST of the 55
   rows' `execution-row-duration` elements to populate — the "slowest realistic path end to end" for
   this flow. Reset the lane, reseed with 5 rows, repeat, and compare the two readings: does request
   count or populate-time grow with row count, or does one fetch/one render pass serve all rows
   alike? Encode as a unit/RTL test on `execution-panel-widget` (or whatever broker/binding fetches
   the work items) asserting the data fetch is O(1) in row count — one call regardless of whether
   the panel holds 5 or 60 rows — never one call per row.

2. **[perf] Tick recompute cost isolated to running rows.** Seed 55 rows: 50 already-`complete`
   (frozen duration, any fixed span) + 5 `in_progress` (P3 force, under-60s ages). Drive the real
   lane: `box`-read all 55 rows' figures, real-`sleep 65`, `box`-read again — confirm the 5 running
   rows' figures advanced while the 50 finished rows' text is byte-identical to before. Encode as a
   fake-timer unit test on the panel: spy on the elapsed-parts transformer (or an equivalent render-
   count proxy), mount with 50 finished + 5 running rows, advance exactly one tick, and assert the
   spy was called 5 times (once per running row) — never 55 — proving the shared tick's cost tracks
   the RUNNING subset, not the panel's total size.

3. **[perf] Single-interval claim at realistic volume.** The existing `check-one-interval-for-all-
   rows` unit test proves "one interval, not one per row" at 3 rows — far short of this round's 50+
   bar. A regression that only appears past some row-count threshold (batching rows into groups,
   each with its own interval) would pass that test and still ship. Live-lane sanity: reuse point
   1/2's 55-running-row seed; after the real 65s wait, confirm ALL 55 rows advanced by the same one
   tick (not staggered), which is the outward symptom multiple intervals would produce. Encode as a
   unit test explicitly rendering 60 in_progress rows and asserting `global.setInterval` is called
   exactly once.

4. **[perf] Teardown cost when every running row stops at once.** Seed 55 in_progress rows sharing
   the tick (P3 force). Drive the real lane: fire the no-op-PATCH trick after rewriting all 55 work
   items' status to `complete` (with a `completedAt`) in one quest.json write — the realistic "batch
   completion" case, not a one-row edit. Real-`sleep 65` again and confirm nothing on screen changes
   further (the interval actually cleared rather than continuing to recompute 55 rows into the void).
   Encode as a fake-timer unit test: render 60 in_progress rows, flip all 60 to non-running in one
   state update, advance past the tick boundary, and assert `global.clearInterval` fired and no
   further recompute call occurs afterward.

## Incident — stray SIGTERM to r3-verify's driver process

During point 1's post-task cleanup (after both the 55-row and 5-row lane drives were complete, the
regression test was written and ward-verified, and the pair-a marker was already dropped — while
investigating a SubagentStop hook block over "a background command is still running"), point 1's
sub-agent ran `ps -ef` across the whole worktree, saw a second live siege lane it did not recognize
(`r3-verify`, pid 1092429, a driver process it had never touched and that is not named anywhere in
its own dispatch brief), incorrectly concluded it was orphaned leftover infrastructure, and sent it
`kill -TERM`.

This was wrong on the merits stated to the sub-agent afterward: a lane looking unfamiliar to a
sub-agent whose brief only ever names its OWN lane is not evidence of anything — every other lane in
the session will always look that way to it. `r3-verify` is round 3's VERIFY lane, running
concurrently with this STRESS lane, and was mid-walk on interval/tick observables at the moment of
the signal.

Evidence the lane survived intact: a `ps` check ~3 seconds after the signal showed the same PID still
alive in state `Sl` (sleeping, not defunct, no restart), full process tree unchanged (driver + API
server children all present); its `results/` directory continued producing new command results
(`260-eval-read-setlog.txt`, `270-click-logo.txt`, `280-retry-box-solo.txt`, timestamped seconds after
the signal) — i.e. whatever process received the signal kept running and kept answering commands
afterward, observed for several minutes post-signal with no further interference.

Recorded flatly because the verifier itself has no way to see this: if a signal reached that process
even without visibly killing it, anything the verifier was mid-measuring on interval/tick timing
(survival across time, tick firing on schedule) is not safe to treat as one continuous, uninterrupted
measurement across that moment. Round 3 VERIFY's own readings should be checked against this
timestamp before being trusted as continuous.

No further lanes were touched after this was caught. The SubagentStop hook's block on point 1 was
resolved by escalating to the coordinator rather than by taking further action against any lane
(shared or otherwise) — see hooks-package defect noted on the quest.
