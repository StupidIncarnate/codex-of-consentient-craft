# Guide: subagent-duration-session-view

Flow entry point: `/:guildSlug/session/:sessionId` (the readonly session transcript, `packages/web`,
route `AppSessionViewResponder` → `SessionViewWidget` → `ChatPanelWidget` readOnly →
`ChatEntryListWidget` → `SubagentChainWidget`). Feature under test: the same
`subagent-chain-duration` element the sibling execution-panel flow covers, rendered here inside a
sub-agent chain header (`SUBAGENT_CHAIN_HEADER`) in a REPLAYED session transcript — frozen once the
sub-agent finished, and **showing nothing at all** while unfinished, because this surface owns no
60-second clock (`dd-session-view-no-tick`).

**Read the sibling guide first if you have not**:
`.quest-plans/d13931f1-d9a4-4f68-aaa9-47c76204708b-guide.md` (flow `subagent-duration-execution-panel`).
LANE DRIVER and RESET below are carried over near-verbatim from it — same siege lane, same
disposal quirks. Every other section is re-derived for THIS route: no work item, no quest.json, no
clock, and different forcing levers.

## LANE DRIVER

One tool: `packages/web/test/siege-driver/siege-driver.ts`. It boots its own API server, Vite
server and headless Chromium on an OS-assigned port pair, with its own throwaway
`DUNGEONMASTER_HOME`. Run every command below from the repo root.

**Start** (pick a lane name unique to your round, e.g. your round id):

```bash
npx tsx packages/web/test/siege-driver/siege-driver.ts <laneName>
```

Prints a manifest to stdout AND writes it to `tmp/siege/<laneName>/lane.json`:

```json
{
  "lane": "<laneName>", "pid": 12345,
  "apiPort": 54321, "webPort": 54322,
  "baseUrl": "http://dungeonmaster.localhost:54322",
  "home": "/tmp/dm-siege-<laneName>-12345",
  "commandsDir": ".../tmp/siege/<laneName>/commands",
  "resultsDir": ".../tmp/siege/<laneName>/results",
  "screenshotDir": ".../tmp/siege/<laneName>/screenshots",
  "idleTimeoutMs": 900000
}
```

`home` is DUNGEONMASTER_HOME **and** HOME for that lane's API server — this is where both the guild
config and the Claude-CLI session JSONL tree live (see OFF-SCREEN). Unlike the execution-panel
flow, no quest tree needs to exist under it for the six walk paths.

**Drive it**: drop one JSON file into `tmp/siege/<laneName>/commands/`, named so it sorts (e.g.
`010-goto.json`), then read the result at the same basename under `results/` (format: `OK` or
`FAIL`, a blank line, then a JSON reading):

```bash
# Write tmp/siege/<laneName>/commands/010-goto.json:
{"name":"goto","target":"/my-guild/session/abc-123","timeoutMs":30000}
# Read tmp/siege/<laneName>/results/010-goto.txt
```

Command set: `goto waitFor click type key paste screenshot box dom storage console network ws eval
file end`. Full behaviour of each: `packages/web/test/siege-driver/siege-command.ts`.

**End**: drop `{"name":"end"}` as the next command, or send SIGINT/SIGTERM to the driver process. If
abandoned, `pkill -f siege-driver`. Ending kills both child servers and deletes the lane's `home` dir
— it does **not** delete `tmp/siege/<laneName>/` itself (see RESET).

Reference: `playbook/smoketest-instances.md` § "Scenario 3: Siege lane".

## ENTRY

Path relative to the lane's own `baseUrl`: **`/<guildSlug>/session/<sessionId>`**.

- `guildSlug` is resolved LOOSELY, not by literal string: `SessionViewWidget` matches
  `guild.urlSlug === guildSlug || guild.id === guildSlug`
  (`packages/web/src/widgets/session-view/session-view-widget.tsx:24,27-29`). So either the raw
  guild id or its `urlSlug` works in the URL — the three subagent-duration session specs
  (`subagent-duration-session-blank/frozen/nested.e2e.ts`) all use the raw `guildId` from
  `guildHarness.extractGuildId`; `subagent-duration-session-no-tick.e2e.ts` uses `urlSlug` via
  `navigationHarness.navigateToSession`. Both are proven.
- **No quest is required at all.** Unlike the execution panel, this route needs no `quest.json`, no
  work item, no `status`, no `startedAt`. It needs only: (1) a guild that exists (`POST
  /api/guilds`), and (2) a session JSONL tree on disk under that guild's encoded path (see SEEDING).
  Landing directly renders whatever is on disk — there is no "start" action, no status gate.
- No auth, no feature flag.
- **Landing signal**: `useSessionReplayBinding` (`packages/web/src/bindings/use-session-replay/use-session-replay-binding.ts`)
  sends `replay-history` over the websocket on open and keeps `isLoading` **true** until
  `chatStreamEnded$` fires for that replay process (line 100-108) — so `SessionViewWidget` renders a
  loading raccoon (`DumpsterRaccoonWidget`) until the WHOLE session file has replayed, then swaps to
  `ChatPanelWidget` (`data-testid="CHAT_PANEL"`). Wait for `CHAT_PANEL`, not for a network response —
  the guilds-list fetch the three main specs wait on (`page.waitForResponse(... '/api/guilds' ...)`)
  is a proxy for "the app booted", not for "the session finished replaying"; `waitFor` on
  `SUBAGENT_CHAIN_HEADER` (or `CHAT_PANEL` first, for a session with no chain at all) is the more
  direct signal for a siege lane, which has no `waitForResponse` command.
- **No guild or no session** renders `data-testid="NOT_FOUND"` instead
  (`session-view-widget.tsx:38-61`) — a good negative-path check but not part of any of the six walk
  paths.

Land in the browser with:
```json
{"name":"goto","target":"/<guildId-or-urlSlug>/session/<sessionId>","timeoutMs":30000}
```
then
```json
{"name":"waitFor","target":"[data-testid=CHAT_PANEL]","timeoutMs":15000}
```
then, for any path expecting a chain, `waitFor` on `[data-testid=SUBAGENT_CHAIN_HEADER]`.

## SEEDING

Everything downstream of `subagent-chain-duration` here is driven off a **Claude session JSONL
transcript alone** — the same `collectSubagentChainsTransformer` the execution panel uses, fed by
`useSessionReplayBinding` instead of the live quest-chat binding. Real field names below.

### 1. Guild, via HTTP (curl)

```bash
API=http://dungeonmaster.localhost:<apiPort>
GUILD_PATH=/tmp/dm-siege-<laneName>-guild   # any absolute dir; mkdir -p it first — riftcarver
                                             # never runs on this flow (no quest exists at all), so
                                             # it needs no .git fixture
mkdir -p "$GUILD_PATH"

curl -s -X POST "$API/api/guilds" -H 'Content-Type: application/json' \
  -d "{\"name\":\"<laneName> guild\",\"path\":\"$GUILD_PATH\"}"
# => { "id": "<guildId>", "urlSlug": "...", ... }
```

That is the entire HTTP surface the six walk paths need.

### 2. Session JSONL, via a tiny tsx script (reuses the proven harness code)

**This is the ONLY route that can write a session JSONL** — reaching for Write or Bash on a
`.claude/projects/**` path is refused outright. Creating any FRESH file under `.claude/projects/**`
is denied session-wide for an agent's own tools: Bash, Write and the WebStorm MCP file-creation tool
all refuse it, with `Permission to use Bash has been denied` / `Permission to use Write has been
denied` / `Permission to use mcp__webstorm__create_new_file has been denied`. Reads (`ls`, Read)
under the same tree succeed. The route that DOES work: write a tiny script under the repo's `tmp/`
(that path is not refused), have that script import the harness, and run it with `HOME=<lane.home>
npx tsx --conditions=source tmp/<script>.ts` — the spawned node process writes the JSONL, and the
refusal does not reach it.

Write `tmp/siege-seed-<laneName>.ts`:

```ts
import { subagentDurationHarness } from '../packages/web/test/harnesses/subagent-duration/subagent-duration.harness';
import { sessionHarness } from '../packages/web/test/harnesses/session/session.harness';

const subagentDuration = subagentDurationHarness({ guildPath: process.argv[2] });
const sessions = sessionHarness({ guildPath: process.argv[2] });

// this-chain, has-start:yes, has-notification:yes — frozen figure.
// Proven values: subagent-duration-session-frozen.e2e.ts's own gap-vs-report precedence recipe.
subagentDuration.seedChain({
  sessionId: 'siege-<laneName>-flat',
  agentId: 'siegeflatagent',
  taskToolUseId: 'toolu_siege_flat',
  taskDescription: 'Session flat chain does the sub-agent work',
  taskToolUseAt: '2026-09-10T02:00:00.000Z',
  notification: { at: '2026-09-10T02:00:45.000Z', durationMs: 270_000 },   // reads "4m"
});

// this-chain, has-start:yes, has-notification:no — no duration figure, chain still renders.
// subagentDuration.seedChain({
//   sessionId: 'siege-<laneName>-blank', agentId: 'siegeblankagent',
//   taskToolUseId: 'toolu_siege_blank', taskDescription: '...',
//   taskToolUseAt: '2026-09-10T02:00:00.000Z',
// });   // omit `notification` entirely

// each-inner-chain — outer chain whose own sub-agent transcript carries a second Task tool-use.
// outerTaskToolUseAt must strictly precede innerTaskToolUseAt (see harness's own header comment).
// subagentDuration.seedNestedChain({
//   sessionId: 'siege-<laneName>-nested',
//   outerAgentId: 'siegenestedouter', outerToolUseId: 'toolu_siege_nested_outer',
//   outerDescription: 'Outer chain holds the nested inner chain',
//   outerTaskToolUseAt: '2026-01-01T11:56:00.000Z',
//   outerNotification: { at: '2026-01-01T11:56:45.000Z', durationMs: 4_380_000 },   // reads "1h13m"
//   innerAgentId: 'siegenestedinner', innerToolUseId: 'toolu_siege_nested_inner',
//   innerDescription: 'Inner chain nests below the outer header',
//   innerTaskToolUseAt: '2026-01-01T11:59:00.000Z',
//   innerNotification: { at: '2026-01-01T11:59:45.000Z', durationMs: 270_000 },   // reads "4m"
// });
// NOTE on the numbers above — see TRAPS "nested bands don't guard precedence" before reusing the
// nested e2e file's own literal timestamps verbatim; the pair here is deliberately reworked so BOTH
// legs' gap and reportedDurationMs land in DIFFERENT bands (proves precedence) while the two chains'
// own figures ("1h13m" vs "4m") stay far enough apart that a copy-the-sibling's-figure bug cannot
// pass unnoticed.

// has-start:"no" substitute — see FORCING. This is NOT a chain with a null start; it is a
// transcript with NO Task tool-use line anywhere, which is the nearest reachable condition.
// sessions.createSessionWithAssistantText({
//   sessionId: 'siege-<laneName>-no-task-line',
//   text: 'No sub-agent was ever dispatched for this reply.',
// });
```

Run it with `HOME` set to the lane's own `home` (from `lane.json`) — both harnesses resolve the
JSONL directory from `os.homedir()`, which reads `HOME`:

```bash
HOME=<lane.home> npx tsx --conditions=source tmp/siege-seed-<laneName>.ts "$GUILD_PATH"
```

### 3. Optional: quest + work item, ONLY for the cross-surface same-test-id check

`check-session-duration-same-test-id` is the one observable on this flow that legitimately needs a
quest — it proves the session-view route and the execution panel render the identical
`subagent-chain-duration` element for the SAME sessionId. Proven recipe:
`subagent-duration-session-no-tick.e2e.ts`'s second test (`:76-175`). Create the quest via
`POST /api/quests`, then write `quest.json` with the work item's `status: "complete"` (not
`"in_progress"`) and `sessionId` set to the same session you seeded in step 2 — `complete` is
deliberate, see TRAPS (orphan-reset). If you script this with `questHarness.writeQuestFile`
(the same harness family, same WRITE WALL workaround) it appends the `event-outbox.jsonl` line for
you (`quest.harness.ts:447-453`); a hand-written raw overwrite of `quest.json` would not, and needs
the manual append the sibling guide documents.

## RESET

Between two paths in the **same** lane:

```bash
for id in $(curl -s "$API/api/guilds" | node -e 'process.stdin.resume();let d="";process.stdin.on("data",c=>d+=c);process.stdin.on("end",()=>JSON.parse(d).forEach(g=>console.log(g.id)))'); do
  curl -s -X DELETE "$API/api/guilds/$id"
done
```

**What this does NOT reset** (the part that surprises people):

- The guild's actual **path directory on disk** (`$GUILD_PATH` above) is untouched — deleting a
  guild only removes its config entry.
- The **session JSONL files** under `<home>/.claude/projects/<encoded guildPath>/` survive guild
  deletion. Reusing a `sessionId` from a prior path in the same lane replays stale/duplicate
  entries. Use a fresh `sessionId` per path (every worked example above already does).
- Ending the lane (`{"name":"end"}`) deletes the lane's `home` (guild tree + session JSONL, fully
  reset) but **not** `tmp/siege/<laneName>/` itself — `results/`, `screenshots/`, `api-server.log`
  and `web-server.log` all persist/append across lane restarts under the same name. Only `commands/`
  is cleared, and only on the NEXT boot of that same lane name. A full reset is a new lane name.
- **The orphan-reset trap does NOT fire for any of the six walk paths** — none of them create a
  work item at all, so there is nothing for `questOrphanResetBroker` to sweep. It only becomes
  relevant if you also seed the optional cross-surface quest (SEEDING §3), and that recipe already
  avoids it by seeding `status: "complete"` rather than `"in_progress"` — see TRAPS.

## CONTROLS

| Test id / selector | What it is |
|---|---|
| `CHAT_PANEL` | The whole readonly transcript panel — wait for this after `goto` (see ENTRY) |
| `NOT_FOUND` | Rendered instead of `CHAT_PANEL` when the guild or session does not resolve |
| `SUBAGENT_CHAIN` | The whole chain box (header + body) — same shared widget as the execution panel |
| `SUBAGENT_CHAIN_HEADER` | The chain's header row — description text, then `subagent-chain-duration` if present |
| `subagent-chain-duration` | **The element under test** — identical test id on both surfaces (`check-session-duration-same-test-id`) |
| `SUBAGENT_CHAIN_SHOW_EARLIER_TOGGLE` | Tail-window toggle inside an expanded chain (not itself part of this feature, but shares the header) |

**No click needed to see a chain's duration.** `SubagentChainWidget` seeds `expanded` as
`useState(true)` (`subagent-chain-widget.tsx:75`) — every chain in the session transcript starts
open. There is no execution-row-style "in_progress auto-expands, complete/failed needs a click"
distinction here, because there are no rows at all. The frozen spec's own header click
(`subagent-duration-session-frozen.e2e.ts:85-87`) is a COLLAPSE-then-RE-EXPAND, used only to force a
React re-render at a later wall-clock time — never an initial open.

Siege `click`/`waitFor`/`dom` commands take these as CSS attribute selectors, e.g.
`[data-testid="subagent-chain-duration"]`.

## OFF-SCREEN

- Main session JSONL: `<lane.home>/.claude/projects/<encoded guildPath>/<sessionId>.jsonl`, where
  "encoded" replaces every non-alphanumeric character in the absolute guild path with `-`
  (`claudePathSlugEncoderTransformer`, `packages/shared/src/transformers/claude-path-slug-encoder/`).
- Sub-agent JSONL: `.../<sessionId>/subagents/agent-<agentId>.jsonl` (siblings of the main file).
- **No quest.json and no event-outbox for the six walk paths** — nothing on disk under
  `<lane.home>/guilds/**` needs to exist at all. Only the optional cross-surface check (SEEDING §3)
  touches `<lane.home>/guilds/<guildId>/quests/<questFolder>/quest.json` and
  `<lane.home>/event-outbox.jsonl`.
- API server log: `tmp/siege/<laneName>/api-server.log`.
- Web (Vite) server log: `tmp/siege/<laneName>/web-server.log`.
- Screenshots: `tmp/siege/<laneName>/screenshots/<file>.png` (via the `screenshot` command).

## FORCING

Per `force:` label in the PATHS block — three levers only on this flow:

- **chain scope: "this chain"** → `subagentDurationHarness.seedChain(...)` (one top-level chain).
  **"each inner chain"** → `subagentDurationHarness.seedNestedChain(...)` (outer chain whose own
  sub-agent transcript carries a second Task tool-use). Scope every assertion to the matching
  `SUBAGENT_CHAIN_HEADER` filtered by description text. `subagent-duration-session-nested.e2e.ts` has
  the exact locator recipe: `outerChainScope = page.getByTestId('SUBAGENT_CHAIN').first()`, built
  from `page` and relying on DOCUMENT ORDER (the outer chain wraps the inner one, so it is first in
  the DOM — `:99-109`'s own comment) — never a text filter for the OUTER scope, since the inner
  header's own description text also lives inside the outer box's subtree once nested, which a text
  filter cannot distinguish from the outer's. `outerHeader`/`innerHeader` are THEN
  `outerChainScope.getByTestId('SUBAGENT_CHAIN_HEADER').filter({ hasText: ... }).first()` (`:114-121`)
  — note this file uses `hasText` (a string), not a `has:` locator, so the ancestor-scoped `has:`
  pitfall documented on the execution-panel sibling's nested spec does not recur here verbatim (see
  TRAPS for what does).

- **has-start: "yes"** → a `Task` tool-use line exists in the transcript (default of `seedChain`/
  `seedNestedChain`). **"no" is UNREACHABLE as the literal branch draws it — do not spend a round
  hunting for a seed shape.** `collect-subagent-chains-transformer.ts:152` sets `taskToolUse: entry`
  unconditionally off an already Task-matched entry, and `chat-entry-contract.ts:39` makes
  `timestamp` a required, non-nullable field on every `ChatEntry` variant, so no real transcript can
  produce a rendered `SUBAGENT_CHAIN` carrying a null or missing Task tool-use timestamp. Two
  separate flowrider passes confirmed this and signed `branch:session-no-start` `unconfirmable`
  rather than force it (quest-summary note `session-view-no-start-branch-unreachable`) — the
  identical unreachability was independently recorded on the sibling execution-panel flow's own
  `no-start` branch, so this is one architectural fact, not two gaps. **The nearest reachable
  substitute**, already proven at `subagent-duration-session-blank.e2e.ts:105-144` (its "EMPTY" case):
  seed a transcript with **no Task tool-use line at all** —
  `sessionHarness.createSessionWithAssistantText({ sessionId, text })` — which renders `SUBAGENT_CHAIN`
  count 0 and `subagent-chain-duration` count 0. That is a transcript with no chain, not a chain with
  no start; sign the literal branch `unconfirmable` and point at this substitute, exactly as both
  prior flowrider passes did.

- **has-notification: "yes"** → `notification` key present on `seedChain`/`seedNestedChain`
  (`{ at, durationMs }`). Precedence note: `reportedDurationMs` (the notification's `durationMs`)
  beats the Task-to-notification timestamp gap (`subagent-duration-label-transformer.ts:30-34`), and
  this flow's own suite guards that precedence directly at
  `subagent-duration-session-frozen.e2e.ts:42-52`: a 45-second gap (band `<1m`) against a reported
  `270_000`ms (band `4m`) reads `4m` — proving the report won, not the gap. **"no"** → omit the
  `notification` key entirely — proven at `subagent-duration-session-blank.e2e.ts`'s un-notified
  sibling chain (`:41-47`) and at `subagent-duration-session-no-tick.e2e.ts:45-51`.

There is no "row-running" or "now-available" lever on this flow at all (unlike the execution panel):
this route threads no `now` into `SubagentChainWidget` under any seed, ever — see TRAPS.

## TRAPS

- **The `.claude/projects/**` WRITE WALL.** An agent's own Write tool, Bash, and the WebStorm MCP
  file-creation tool are ALL denied when creating a fresh file under `.claude/projects/**`. Reads are
  fine. The one route that works is a tiny script under the repo's `tmp/`, run as `HOME=<lane.home>
  npx tsx --conditions=source tmp/<script>.ts`, which imports the harness and lets the spawned node
  process do the writing. A walker who does not know this loses an hour to it.

- **The `session-no-start` branch cannot be reached — do not hunt for a seed shape.** See FORCING
  above for the exact substitute (`subagent-duration-session-blank.e2e.ts`'s no-Task-line case) and
  cite the same reasoning both prior flowrider passes recorded
  (quest-summary note `session-view-no-start-branch-unreachable`) rather than re-deriving it a third
  time.

- **The nested spec's own literal numbers do NOT guard precedence — do not copy them verbatim if your
  path needs to.** `subagent-duration-session-nested.e2e.ts:86,91` seeds both chains so their
  Task-to-notification GAP lands in the SAME band as their own `reportedDurationMs` (outer: gap ≈
  1h13m, report 4,380,000ms = 1h13m; inner: gap ≈ 4m30s, report 270,000ms = 4m). Inverting
  `subagent-duration-label-transformer.ts`'s precedence ternary would leave that spec green
  (quest-summary note `session-view-nested-spec-bands-do-not-test-precedence`). It still correctly
  proves `check-session-nested-duration` (two DIFFERENT figures, one per header) — it just proves
  nothing about precedence. If your walk needs a nested precedence guard, use the SEEDING §2 recipe
  above instead: both legs' gap and `durationMs` land in different bands (same shape
  `subagent-duration-session-frozen.e2e.ts` already proves for a flat chain), and the two chains'
  resulting figures (`1h13m` vs `4m`) are far enough apart that a copy-the-sibling's-figure bug could
  not pass unnoticed either.

- **There is no clock on this route to fast-forward, and that is the whole point of dd-session-view-no-tick.**
  `ChatPanelWidgetProps` (`chat-panel-widget.tsx:32-48`) carries no `now` field at all — not "usually
  absent", structurally absent from the prop type every caller of `ChatPanelWidget` fills in. So
  there is nothing to seed to make a figure live, and no `page.clock` state that would matter even if
  the siege lane exposed one (it doesn't — same as the execution-panel sibling). Proving a duration
  stays FROZEN here means proving the absence of a ticking mechanism, not fast-forwarding a real one:
  `subagent-duration-session-frozen.e2e.ts:54,80,85-87` combines a full hour of fake-clock
  advancement (irrelevant to the figure, since nothing reads it) with a collapse/re-expand click
  (which forces React to actually re-render) and reads the identical text both times. In a siege lane
  with no fake clock, the collapse/re-expand click alone is the load-bearing half — do it before
  trusting a "still 4m after a while" reading.

- **`ChatPanelWidget` itself owns an UNRELATED `setInterval`, for the raccoon sprite bounce
  animation** (`chat-panel-widget.tsx:81-97`, period from `raccoonAnimationIntervalTransformer`, NOT
  `elapsedDisplayConfigStatics.refresh.tickMs`). A hand-rolled "count every setInterval call" counter
  that does not filter on the exact tick period (60,000ms) will false-positive
  `check-session-registers-no-interval` as failing. `sessionSubagentDurationHarness.installIntervalCounter`
  already filters on `timeout === tickMs` for exactly this reason
  (`session-subagent-duration.harness.ts:56-61`) — reuse that filter, do not write a bare counter.

- **Siege's `eval` has no `page.addInitScript` equivalent, so a manual siege-lane reproduction of
  `check-session-registers-no-interval`'s negative half is unproven.** `siege-command.ts`'s `'eval'`
  case is a plain `await page.evaluate(value)` (`:317-320`), which only runs AFTER `goto` resolves —
  it cannot patch `window.setInterval` before the app's own initial mount the way
  `page.addInitScript` does. In THIS flow specifically the risk is low (there is structurally no
  `now` prop to gate a tick on — see the clock trap above — so nothing can register at the tick
  period regardless of when you patch), but it is not the same rigor as the automated spec. The safe
  answer: run `npx playwright test packages/web/src/flows/session-view/subagent-duration-session-no-tick.e2e.ts`
  directly (permitted; see TOOLING) rather than reimplementing the patch inside a siege lane.

- **Real-geometry checks would need a painted tab**, exactly as on the execution-panel sibling, if
  this flow ever grows one (`dd-placement`'s styling parity is signed on the execution-panel side
  today) — issue a `screenshot` command (or at least a `waitFor`) before any `box`/`dom` geometry
  read, since a headless page that has never painted reads every box as zero-sized.
