## Lane instability (infrastructure note, not a product defect)

Four consecutive lane boots died on their own before I could finish driving them, with NO `end`
command ever sent and no process ever signalled by me:

- `r6-verify` — exited code 144 after processing only 2 commands (`goto`, `waitFor`).
- `r6-verify-2` — exited code 1 after 4 commands (`goto`, `waitFor`, 2×`box`), mid-sequence.
- `r6-verify-3` — exited code 1 after 4 commands (`goto`, `waitFor`, `box`, `eval`), died during
  an idle real-time `sleep 66` with no commands pending — well under the 900000ms idle timeout in
  its own `lane.json`.
- `r6-verify-4` — exited code 1 before processing even its first `goto` command, ~40s after boot.
  A bare, unrelated `sleep 66` in the SAME session also returned exit code 1 at almost exactly the
  same moment `r6-verify-3` died, which points at something reaping this session's whole process
  tree rather than a bug specific to the siege-driver.
- `r6-verify-5` — booted and survived the full walk, including two real ~60s waits.

No server-side error accompanies any of these: `api-server.log` and `web-server.log` for
`r6-verify-2` show a clean orchestration-loop boot with no exception. All four API/Vite servers
came up fine; only the driver's own Node process (or something above it) died. Per this round's
lane-discipline rules this is filed as a `rework`-class defect for the round to note, not chased
further and not treated as a wall (a wall would mean no lane could ever finish a walk — the fifth
one did).

**Guide correction, confirmed by direct testing**: the guide's OFF-SCREEN section says quest.json
under the lane's `home` can be written via "Read/Write/Bash python3/node -e". In this session, ANY
raw Bash command that touches an OS `/tmp` path (which a lane's `home` always is,
e.g. `/tmp/dm-siege-<lane>-<pid>/...`) is denied outright by a permission hook — including
`node -e "fs.writeFileSync('/tmp/...)"` run via Bash. Only the `Write`/`Edit`/`Read` TOOLS (not
Bash) reliably reach a path under OS `/tmp`. Bash `node -e`/`date` that only computes and prints to
stdout (no file write) is fine; anything that WRITES under `/tmp` must go through the Write/Edit
tool, never Bash. This confirms and sharpens the "raw Bash aimed at OS /tmp is denied" note already
flagged as a pending guide fix.
