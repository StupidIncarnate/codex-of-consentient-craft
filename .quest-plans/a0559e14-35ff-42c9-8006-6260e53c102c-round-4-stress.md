(`#negative-span-clamps`) already names the exact failure shape — "the running figure's end point is
the browser's clock while the start comes from the server, so a skewed clock ... " — and the client's
own state-apply path has no defense against an inbound frame that is stale relative to one already
applied.

## PASS 1 — enumerated stress points

1. **[staleness — core] Out-of-order `quest-updated` un-freezes a completed row.** Seed a row
   running under 60s, drive it to `show-final-duration` (completedAt arrives, one `quest-updated`
   frame — call it A — carries the finished work item and lands). Then apply a SECOND frame — call
   it B — for the SAME questId that is chronologically OLDER than A (e.g. a delayed duplicate
   broadcast, or a reconnect replay racing a live update) and still shows the work item
   `in_progress` with no `completedAt`. `setQuest(questParsed.data)` in `use-quest-chat-binding.ts`
   applies B with no check against A. Failure mode: the frozen duration reverts to a live figure (or
   the duration element disappears/starts recomputing), directly violating "unchanged by later
   ticks" and `check-final-replaces-running-immediately`'s own claim that the switch happens once
   and stays. Surface: hook-level test on `useQuestChatBinding`, two `questUpdated$` emissions for
   one questId, second one older-shaped than the first; assert the EXPOSED `quest` after both is the
   one carrying `completedAt`, not whichever arrived last.

2. **[staleness — core] Reconnect during the "under 60s" window can permanently miss a
   completedAt.** Row is running under 60s; the websocket drops; while disconnected, the server
   records `completedAt` (so no live `quest-updated` is ever delivered to this now-offline client);
   the socket reconnects and resubscribes. Failure mode: if reconnect only rearms listening for
   FUTURE mutations rather than pulling the CURRENT quest snapshot, the row is stuck reading `<1m`
   forever — worse than a late update, a silently wrong one that nothing after it will ever correct,
   since the item is already finished and will emit no further `quest-updated`. This is "a page whose
   websocket dropped and reconnected while a row kept running" from the brief, applied to the exact
   edge this path signs (`under-minute-completes`). Surface: hook-level test — WS close/reopen
   sequence where the SERVER-SIDE state changes only during the outage window; assert the
   post-reconnect `quest` reflects the change.

3. **[staleness — core] A backgrounded tab suspends the tick with no resync on refocus.**
   `useElapsedTickBinding` refreshes `now` only on mount and on its own `setInterval` firing — there
   is no `visibilitychange` handler. A hidden tab is throttled or fully suspended by the browser's
   power policy, so the interval can silently stop firing for well over its 60s period. On refocus,
   nothing forces an immediate `Date.now()` read; the figure stays pinned to whatever `now` the last
   successful tick produced until the NEXT scheduled fire (which may itself be delayed further by the
   same throttling). This band is exactly where that reads worst: a row stuck at `<1m` for several
   real minutes after the user returns to the tab looks broken, where a stuck `4m` merely looks slow.
   Surface: hook-level test on `useElapsedTickBinding` — simulate a suspended interval (never invoke
   the scheduled callback) across a `document.visibilitychange` → `visible` event, assert whether
   `now` is recomputed by that event (today, it is not).

4. **[replay] A duplicate/replayed `quest-updated` for an UNCHANGED completedAt causes a visible
   reset.** The no-op-PATCH forcing trick, or any flaky retry on the server's broadcast path, can
   fire the identical finished-state frame twice in a row for the same work item. Failure mode: does
   the second, informationally-redundant `setQuest` call cause a transient unmount/remount of
   `execution-row-duration` (React reconciliation losing key continuity) or reset any of the row's
   own local state (e.g. `expanded`) even though nothing about the work item actually changed?
   Surface: hook- or widget-level test applying the identical quest value via two sequential
   `quest-updated` frames, asserting no drop of the duration element and no reset of derived local
   state between the two.

5. **[concurrency × staleness] Two `quest-updated` frames for the same work item land back-to-back
   with no ordering guarantee made explicit anywhere.** Fire two payloads in the same tick/microtask
   for one questId — one with `completedAt` absent (still running), one with it present — with no
   delay between them, in BOTH arrival orders. Failure mode: `setQuest` is last-write-wins by
   construction (React state), which is only correct if the SOURCE stream is guaranteed in-order;
   nothing in `use-quest-chat-binding.ts` asserts or documents that guarantee, so a future change to
   how the server batches/broadcasts (or a second producer) breaks this silently. Surface: pin the
   CURRENT behaviour (last frame wins) as a named, asserted contract at the hook level in both
   orders, so a change that flips it is caught here instead of surfacing as an intermittent frozen-
   duration flicker in production.

Vectors considered and not carried forward for this path: **hostile-input** and **configuration**

narrow path adds no new malformed-input or config surface beyond what those cover. **perf** needs a

scaling question — the tick-at-scale unit (`check-one-interval-for-all-rows`) is already `[C✓ F✓ S✓]`
elsewhere on this same flow. **double-submit** and **boundary** are folded into points 1/4/5 above
rather than restated separately, since this path's only "submit" is the completedAt-arrival frame
itself.

check means none of the three effects even re-run on the redundant render, so `userClickedRef.current`
and `expanded` are provably untouched. `elapsedEndPoint = completedAt ?? (isRunning ? now : undefined)`
(line 194) reads straight from props each render, so an unchanged `completedAt` string yields
byte-identical transformer output — the figure cannot flicker between two duplicate frames.
