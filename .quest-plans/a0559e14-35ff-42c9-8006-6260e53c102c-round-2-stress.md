## The real gaps — FAMILY: configuration

Both found by reading `packages/shared/src/contracts/work-item/work-item-contract.ts` and its test
file directly, against P2's own precondition ("startedAt present", "no completedAt and not
in_progress").

1. **`completedAt: null` (explicit, not omitted) on a P2-shaped work item.**
   `work-item-contract.test.ts` (lines 532-561) ALREADY carries a test for the sibling field —
   `describe('startedAt tolerates explicit null the same as an omitted key', ...)` — with a comment
   explaining that a raw `.optional()` on a `z.string().datetime()` field rejects `null` outright,
   and because the quest-load responder has no per-item recovery, that zod throw becomes a
   whole-quest `quest-load-failed`: EVERY row in the execution panel goes blank, not just the one
   field's figure. That test's own scenario is `status: 'in_progress'` (which is really path P1's
   territory once the null strips to absent), and there is NO equivalent test anywhere for
   `completedAt: null` — the exact field P2's own force condition turns on ("no completedAt"). The
   row widget's own gate (`completedAt ?? (isRunning ? now : undefined)`) already treats `null` and
   `undefined` identically via `??`, so if the CONTRACT is the one place null is intolerant, a
   `completedAt: null` value seeded from any real producer (a DB round-trip default, a
   `JSON.parse`/`JSON.stringify` boundary that materializes `null` instead of dropping the key) takes
   down the whole panel instead of degrading to "no figure" the way an omitted key already does.
   Field: `completedAt: z.string().datetime().brand<'IsoTimestamp'>().optional()` — confirmed still
   plain `.optional()`, not `.nullish()`.
   DISPATCH → sub-agent A.

2. **A non-UTC-offset ISO datetime (e.g. `2026-01-01T11:56:00.000+05:00`) for `startedAt` or
   `completedAt` on a P2-shaped work item.** Zod's `z.string().datetime()` rejects an offset suffix
   by default (only bare `Z` passes, unless the schema opts in via `{offset: true}`, which this field
   does not). This is a plausible real-world value shape — any producer that formats a timestamp with
   a local offset instead of normalizing to UTC `Z` (a manually authored value, a library that isn't
   `Date.prototype.toISOString`) breaks the WHOLE quest.json parse for reasons that have nothing to do
   with the row's own duration logic, exactly the failure mode already documented for the null case
   above. No existing test in `work-item-contract.test.ts` touches an offset-suffixed datetime.
   DISPATCH → sub-agent B.

(A candidate "missing milliseconds" case, e.g. `2026-01-01T11:56:00Z`, was considered and DROPPED:
zod's default `z.string().datetime()` has no `precision` option set on this field, and by default
treats milliseconds as optional — so that shape most likely already parses fine. Chasing it further
without solid confirmation would be a padded, unverified point; the offset case above is the same
"plausible malformed producer" idea with an unambiguous, documented zod rejection.)
