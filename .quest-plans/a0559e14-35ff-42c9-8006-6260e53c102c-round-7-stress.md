## PASS 1 — enumerated stress points

Concurrency surface named for this flow: one shared 60-second interval (client), a websocket pushing
row updates, and a server that re-reads quest.json on every broadcast. This path's own two live actions
are (a) a running row showing `Nm` off the shared tick, and (b) that same row's `completedAt` landing
mid-walk via the no-op-PATCH forcing trick, which is this repo's only reliable way to wake an
already-open page (see guide TRAPS). Every point below targets one of those two actions, or the seam
between them.

Note up front: the family's own text calls out "two browser tabs on the same quest at once" as worth
driving. The siege lane holds exactly one Chromium page for this whole session — there is no second
tab reachable through the file-drop protocol. Two tabs reading the same broadcast is a special case of
"two readers, one writer" — the real risk is whether the server's read-then-broadcast is safe under
concurrent writers, which points 1, 2, 3 and 5 below test directly at the HTTP/broadcast layer. A
literal dual-tab UI check is therefore folded into those rather than listed as its own unreached point.

1. **Concurrent no-op PATCHes racing the persist-and-broadcast read.** Fire two
   `PATCH /api/quests/<questId>` requests with the identical no-op body
   (`{"status":"in_progress"}`) back-to-back with no gap, at the instant this row's `completedAt` has
   just been written to quest.json on disk. Does the server's read-then-broadcast serialize so both
   responses/broadcasts reflect the same final `completedAt`, or can promise interleaving let the
   SECOND-fired request's read start before the first one's read finishes, race ahead, and broadcast
   first — landing the browser on a broadcast that is not strictly ordered after the file write, i.e. a
   lost update? Surface: whichever server broker reads quest.json and pushes the websocket frame after
   a PATCH.

2. **Two different-bodied PATCHes fired at the same instant.** One process fires the no-op status PATCH
   used to force the completedAt broadcast; in the same instant a second PATCH targets the SAME quest
   with a different field (a second no-op, or a pause). Because both share one quest.json, does the
   broadcast either process ends up sending reflect a real, fully-written state — or can it reflect an
   intermediate merge where one write's side effect (e.g. pause resetting the row's status) is visible
   without the other's (the row's completedAt), producing a rendered figure that matches neither writer
   — "a row that renders a value neither writer wrote."

3. **Rapid repeated no-op PATCH, zero gap, at the completion instant.** Fire five identical no-op
   PATCHes back-to-back (no delay) against the quest right as this row's completedAt lands in
   quest.json. If the broadcast path coalesces or debounces rapid triggers, could the ONE broadcast that
   would have carried the fresh completedAt be the one that gets dropped, leaving the row stuck showing
   its live `Nm` figure forever even though the file already holds `completedAt` (a stuck, never-frozen
   row) — a half-applied update from the client's point of view.

4. **Shared tick firing in the same window completedAt is delivered.** The 60-second interval
   (`useElapsedTickBinding`) recomputes every visible running row from a `visibleWorkItems`/
   `hasRunningWorkItem` snapshot. If that snapshot is captured once at effect-setup time (a stale
   `setInterval` closure) rather than read fresh on every fire, then the FIRST tick after this row's
   completedAt arrives could still treat the row as running and recompute a live `now`-based figure,
   overwriting the just-frozen final duration on the very next 60s boundary. This directly probes the
   single-shared-tick design decision under a concurrent state update, and is real product-code risk
   this path can drive: seed completion, wait one more real tick (65s), and check the figure did NOT
   move.

5. **Quest.json read mid-write from an unrelated concurrent mutation.** This row's completedAt write
   lands in the SAME quest.json file as every other row and every other mutation. Fire a second,
   unrelated no-op PATCH microseconds apart from the write that lands this row's completedAt (simulating
   a second caller touching the same quest at once). Because Node's `fs.writeFile` is not atomic unless
   the writer renames into place, could a reader triggered by the unrelated PATCH observe a torn/partial
   JSON mid-write — surfacing as a `quest-load-failed` broadcast that blanks the WHOLE panel (not just
   this row), rather than either the fully-old or fully-new state?

All five are reachable from this lane: 1, 2, 3 and 5 are driven with `curl` against the lane's own API
port (real concurrent HTTP, no browser needed for the write side — the browser is only used afterward
to read what actually rendered); 4 is driven by seeding completion and using a real 65s wait, exactly as
the guide's FORCING section prescribes for the tick transition.

### Point 3 — rapid repeated no-op PATCH, broadcast coalescing — confirmed, no gap

LOOKED: `packages/orchestrator/src/brokers/quest/outbox-watch/quest-outbox-watch-broker.ts` — for every
`onLine` off the tail it does exactly one `safeParse` + one `onQuestChanged({questId})` call,

`state.reading`/`pendingDrain` guard: a `change` event arriving mid-read sets `pendingDrain=true` and

appended during the busy window is still captured by the next drain and every line still gets its own
`onLine` call. This coalesces the EVENT, never the DATA — it cannot silently drop a line. Already has
green coverage of this exact path in `fs-watch-tail-adapter.test.ts` ("EDGE: second change event while
reading => ignored until first read completes").

LOOKED: `questPersistBroker` — writes to `${questFilePath}.tmp` (plain `fs/promises writeFile`), then

`orchestratorLoadQuestAdapter`) needs no lock, since `rename()` guarantees any concurrent open+read sees
either the fully-old or fully-new file, never a torn mix. As a second layer,
`server-init-responder.ts`'s outbox-driven `onQuestChanged` handler catches a load failure into a log
line (`processDevLogAdapter`) rather than propagating it — a failed read there cannot blank the browser.
